# AI Service 接口文档

## 1. 文档范围

本文档对应当前仓库中的 `ai_backend/ai_service`，用于给主游戏后端提供 AI 玩家初始化、记忆管理、人格配置和阶段决策能力。

- 服务类型：FastAPI
- 默认端口：`8001`
- Swagger：`http://localhost:8001/docs`
- 健康检查：`GET /health`

## 2. 启动方式

建议从仓库根目录启动：

```bash
uv run uvicorn ai_backend.ai_service.app:app --reload --host 0.0.0.0 --port 8001 --no-access-log
```

启动后先验证：

```bash
curl http://localhost:8001/health
```

返回：

```json
{
  "status": "ok",
  "service": "ai_service"
}
```

## 3. 统一响应结构

除 `GET /health` 外，其余接口统一返回：

```json
{
  "code": 200,
  "message": "ok",
  "timestamp": 1777425734218,
  "data": {}
}
```

说明：

- `code`：业务层返回码，正常为 `200`
- `message`：通常为 `ok`
- `timestamp`：毫秒时间戳
- `data`：实际业务数据

## 4. 关键行为说明

### 4.1 AI 玩家 ID 规则

服务内部默认生成的 AI 玩家 ID 为：

- `ai_1`
- `ai_2`
- `ai_3`

注意必须带下划线 `_`。  
例如 `personaAssignments` 和 `roles/assign` 中应传 `ai_1`，不能传 `ai1`。

### 4.2 LLM 自动绑定规则

当调用 `generate` 或 `bootstrap` 时：

- 如果请求显式传了 `modelPolicy`，会优先按该策略决定 `provider / model_name / base_url`
- 如果未传 `modelPolicy`，会读取 `.env` 中的默认模型配置
- 如果 `MODEL_PROVIDER=openai` 且 `OPENAI_PLAYER_MODE=per-player`，会按 `OPENAI_API_KEY_P1..Pn`、`OPENAI_MODEL_NAME_P1..Pn`、`OPENAI_BASE_URL_P1..Pn` 为每个 AI 绑定独立 LLM

这些绑定的 `apiKey` 只保存在服务端，不会通过 `players` 接口返回。

### 4.3 invoke 自动补全规则

调用 `POST /internal/ai/agent/invoke` 时：

- 如果请求未传 `llm`，服务会根据 `gameId + aiId` 读取生成阶段绑定好的 LLM
- 如果请求未传 `persona`，服务会从已生成玩家档案中读取
- 如果请求未传 `role`，服务会从已同步的角色信息中读取

前提是这局已经先调用过 `generate` 或 `bootstrap`，并且角色已通过 `roles/assign` 同步。

### 4.4 seat 字段说明

当前 `generate/bootstrap` 返回的 `players[*].seat` 只是 AI 服务内部按 `1..N` 顺序生成的序号，不一定等于主游戏房间里的真实座位号。

因此：

- 主游戏后端必须自己维护真实的 `seat -> aiId` 映射
- 不要直接把 AI Service 返回的 `seat` 当成房间真实座位

## 5. 接口列表

### 5.1 生成 AI 玩家

`POST /internal/ai/players/generate`

用途：

- 为某局生成若干 AI 玩家档案
- 绑定每个 AI 的服务端 LLM 配置
- 默认把每个 AI 的 `persona` 设为 `logical`

请求体：

```json
{
  "gameId": "game1",
  "roomId": "room1",
  "aiCount": 2,
  "modelPolicy": {
    "provider": "openai",
    "model_name": "gpt-4.1-mini",
    "base_url": "https://api.openai.com/v1"
  }
}
```

说明：

- `modelPolicy` 可省略
- 省略时会自动读取 `.env`

返回 `data` 示例：

```json
{
  "gameId": "game1",
  "roomId": "room1",
  "players": [
    {
      "ai_id": "ai_1",
      "game_id": "game1",
      "room_id": "room1",
      "seat": 1,
      "role": null,
      "persona": "logical",
      "model_provider": "openai",
      "model_name": "gpt-4.1-mini",
      "model_base_url": "https://api.openai.com/v1"
    },
    {
      "ai_id": "ai_2",
      "game_id": "game1",
      "room_id": "room1",
      "seat": 2,
      "role": null,
      "persona": "logical",
      "model_provider": "openai",
      "model_name": "gpt-4.1-mini",
      "model_base_url": "https://api.openai.com/v1"
    }
  ]
}
```

### 5.3 批量同步角色

`POST /internal/ai/players/roles/assign`

用途：

- 主游戏后端在分配完角色后，把 AI 的最终身份同步给 AI Service
- 之后 `invoke` 可以自动知道“你是什么角色”

请求体：

```json
{
  "gameId": "game1",
  "assignments": [
    { "aiId": "ai_1", "role": "werewolf" },
    { "aiId": "ai_2", "role": "seer" }
  ]
}
```

返回 `data` 示例：

```json
{
  "gameId": "game1",
  "assignments": [
    { "aiId": "ai_1", "role": "werewolf" },
    { "aiId": "ai_2", "role": "seer" }
  ]
}
```

说明：

- 只有匹配到的 AI 玩家才会被写入
- 如果一个都没匹配到，会返回 `404`

### 5.4 初始化记忆

`POST /internal/ai/memory/init`

用途：

- 为一局中的多个 AI 初始化记忆状态

请求体：

```json
{
  "gameId": "game1",
  "players": ["ai_1", "ai_2"],
  "asyncMode": true
}
```

返回 `data` 示例：

```json
{
  "gameId": "game1",
  "initialized": ["ai_1", "ai_2"],
  "asyncMode": true
}
```

说明：

- `asyncMode=true` 时会异步重算可疑度

### 5.5 广播公共游戏事件

`POST /internal/ai/game/events/broadcast`

用途：

- 将一条所有玩家都能观察到的公共事件广播给同局多个 AI
- 适合白天发言、投票动作、投票结果、死亡结果、系统公告等共享历史
- 比循环调用 `POST /internal/ai/memory/event` 更适合主后端统一落公共事件

请求体：

```json
{
  "gameId": "game1",
  "event": {
    "day": 1,
    "stage": 2,
    "eventType": "vote",
    "speaker": "player_5",
    "content": "vote -> player_2",
    "weight": 1.0,
    "targets": ["player_2"]
  },
  "aiIds": ["ai_1", "ai_2"],
  "candidateTargets": ["player_1", "player_2", "ai_1", "ai_2"],
  "asyncMode": true
}
```

返回 `data` 示例：

```json
{
  "gameId": "game1",
  "event": {
    "eventId": "evt_vote_001",
    "day": 1,
    "stage": 2,
    "eventType": "vote",
    "speaker": "player_5",
    "content": "vote -> player_2",
    "weight": 1.0,
    "timestamp": 1777425734218,
    "targets": ["player_2"]
  },
  "appliedAiIds": ["ai_1", "ai_2"],
  "states": {
    "ai_1": {
      "gameId": "game1",
      "aiId": "ai_1",
      "memoryWindow": [],
      "longSummary": "",
      "relations": {},
      "suspicionScores": {},
      "lastDecisions": [],
      "updatedAt": 1777425734218
    }
  },
  "asyncMode": true
}
```

说明：

- `aiIds` 可省略；省略时默认广播给当前局全部 AI
- 如果传了 `aiIds`，服务端会自动过滤掉不属于当前局的 AI
- 如果过滤后没有任何目标 AI，会返回 `404 No AI players found for this game`
- 当同时传入 `candidateTargets` 且 `asyncMode=false` 时，会同步重算每个目标 AI 的 `suspicionScores`

### 5.6 追加记忆事件

`POST /internal/ai/memory/event`

用途：

- 向某个 AI 的记忆中追加一条事件

```json

  "aiId": "ai_1",

  "candidateTargets": ["ai_2", "ai_3"],
```

返回 `data` 为更新后的完整 `AgentMemoryState`，包含：

- `memoryWindow`
- `longSummary`
- `relations`
- `suspicionScores`
- `lastDecisions`

### 5.12 阶段决策调用

`POST /internal/ai/agent/invoke`

用途：

- 在发言、投票、夜晚技能等阶段调用大模型生成 AI 决策

请求体：

```json
{
  "requestId": "req_10001",
  "gameId": "game1",
  "aiId": "ai_1",
  "stage": "speech",
  "role": "villager",
  "persona": "logical",
  "llm": {
    "provider": "openai",
    "modelName": "gpt-4.1-mini",
    "apiKey": "sk-xxx",
    "baseUrl": "https://api.openai.com/v1",
    "temperature": 0.3,
    "maxTokens": 512,
    "timeoutSeconds": 12
  },
  "visibleEvents": [],
  "alivePlayers": ["ai_1", "player_1", "player_2"],
  "candidateTargets": ["player_1", "player_2"],
  "privateVision": {},
  "callbackUrl": "http://node-backend:3000/api/internal/ai/callback",
  "asyncMode": true
}
```

当前代码中的关键规则：

- `llm` 可省略
- `persona` 可省略
- `role` 可省略
- `nightAction` 为夜晚阶段的结构化动作体
- 省略时服务会尝试自动从已生成玩家档案中补全
- 如果没有先生成玩家且又没传 `llm`，会返回 `404`

夜晚阶段返回时，推荐主后端读取：

- `decision.skillType`
- `decision.skillTarget`
- `decision.nightAction`

其中 `decision.nightAction` 的结构为：

```json
{
  "killTarget": null,
  "inspectTarget": null,
  "saveTarget": null,
  "poisonTarget": null,
  "passReason": null
}
```

推荐的 `privateVision` 约定：

- 狼人：
  - `wolfTeammates`: 狼队队友列表，可包含 AI 和真人玩家
  - `wolfChat` 或 `teammateMessages`: 队友讨论内容
  - `consensusTarget`: 当前狼队协商后的优先击杀目标
  - `allowFriendlyFire`: 是否允许误伤狼队，默认应为 `false`
- 女巫：
  - `nightDeathCandidate`: 今晚被刀的玩家
  - `antidoteAvailable`: 解药是否还可使用
  - `poisonAvailable`: 毒药是否还可使用
- 预言家：
  - 可只传正常 `candidateTargets`
  - 服务会结合 memory 自动避免重复查验已查过的对象
- 猎人：
  - 触发阶段应使用 `stage = "death_shot"`
  - `hunterCanShoot`: 本次死亡是否允许开枪
  - `hunterShotUsed`: 是否已经用过技能
  - `deathReason`: 死亡原因，例如 `vote`、`werewolf_kill`、`witch_poison`
  - 如果 `deathReason = "witch_poison"`，服务会自动判定为不能发动技能

`asyncMode=true` 返回 `data` 示例：

```json
{
  "requestId": "req_10001",
  "accepted": true,
  "asyncMode": true,
  "callbackUrl": "http://node-backend:3000/api/internal/ai/callback"
}
```

`asyncMode=false` 返回 `data` 示例：

```json
{
  "requestId": "req_10001",
  "gameId": "game1",
  "aiId": "ai_1",
  "stage": "speech",
  "decision": {
    "actionType": "speech",
    "speechText": "我目前更想听大家对 2 号和 5 号的解释。",
    "voteTarget": null,
    "skillType": null,
    "skillTarget": null,
    "confidence": 0.73,
    "explain": ["public_info_consistent"]
  },
  "suspicionScores": [],
  "latencyMs": 1421,
  "fallbackUsed": false,
  "errorCode": null
}
```

回调体与同步返回 `data` 结构一致。

### 5.13 invoke 的 stage 取值

当前代码支持：

- `speech`
- `vote`
- `night_action`
- `death_shot`

## 6. 主游戏后端接入时机

这一节是给主游戏后端同学的实际接入说明。

### 6.1 总原则

- 前端只调用主游戏后端
- 主游戏后端负责业务编排
- 主游戏后端内部调用 AI Service
- AI Service 不直接管理房间、真人玩家和主状态机推进

### 6.2 开始游戏时调用什么

在主游戏后端“开始游戏”时：

1. 先根据房间目标人数和当前真人入座人数，计算需要补多少 AI
2. 生成真实的 `seat -> aiId` 映射
3. 调用 `POST /internal/ai/bootstrap`

推荐做法：

- 如果模型配置全部走 `.env`，`bootstrap` 不传 `modelPolicy`
- 如果本局需要覆盖模型，再显式传 `modelPolicy`
- 如果要指定某些 AI 的人格，就传 `personaAssignments`

### 6.3 角色分配完成后调用什么

主游戏后端在完成身份分配后，立即调用：

- `POST /internal/ai/players/roles/assign`

用途：

- 把 `ai_1 -> werewolf`、`ai_2 -> seer` 这类结果同步给 AI Service
- 后续 `invoke` 才能自动带上角色 prompt

### 6.4 每个阶段事件落地后调用什么

当主游戏后端产生新的阶段事件后，应按事件可见范围选择：

- 公共事件优先调用 `POST /internal/ai/game/events/broadcast`
- 只有明确要写入某一个 AI 的定向记忆时，才调用 `POST /internal/ai/memory/event`

典型事件包括：

- 白天发言
- 白天投票
- 夜晚技能结果
- 公开死亡结果
- 私有视野信息变更

建议：

- 谁需要记住这条信息，就给谁写入 memory
- 如果这条事件会影响目标判断，就带上 `candidateTargets`
- 对“所有人都能看到”的事件，优先一次性广播，而不是在主后端循环调单 AI 接口
- 私有角色信息优先通过 `invoke` 的 `privateVision` 传递，不要伪装成公共事件广播

### 6.5 轮到 AI 行动时调用什么

当某个 AI 轮到行动时，调用：

- `POST /internal/ai/agent/invoke`

典型场景：

- 白天发言
- 白天投票
- 夜晚技能使用

建议传入：

- `requestId`
- `gameId`
- `aiId`
- `stage`
- `visibleEvents`
- `alivePlayers`
- `candidateTargets`
- `privateVision`
- `callbackUrl`

如果已经做过 `bootstrap + roles/assign`，通常不需要再传：

- `llm`
- `persona`
- `role`

### 6.6 建议时序

推荐最小联调顺序：

1. 主后端开始游戏
2. 主后端计算 `aiCount`
3. 主后端调用 `POST /internal/ai/bootstrap`
4. 主后端完成角色分配
5. 主后端调用 `POST /internal/ai/players/roles/assign`
6. 每轮有新的公共事件时调用 `POST /internal/ai/game/events/broadcast`
7. 只有需要定向写入单个 AI 记忆时，才调用 `POST /internal/ai/memory/event`
8. 轮到 AI 发言/投票/放技能时调用 `POST /internal/ai/agent/invoke`
9. AI Service 通过同步响应或 callback 返回决策
10. 主后端消费决策并推进游戏状态

## 7. 推荐的主后端 callback 接口

AI Service 在 `asyncMode=true` 且传了 `callbackUrl` 时，会把结果 POST 回主后端。

主后端建议提供内部接口，例如：

`POST /api/internal/ai/callback`

回调体示例：

```json
{
  "requestId": "req_10001",
  "gameId": "game1",
  "aiId": "ai_1",
  "stage": "speech",
  "decision": {
    "actionType": "speech",
    "speechText": "我目前更想听大家对 2 号和 5 号的解释。",
    "voteTarget": null,
    "skillType": null,
    "skillTarget": null,
    "confidence": 0.73,
    "explain": ["public_info_consistent"]
  },
  "suspicionScores": [],
  "latencyMs": 1421,
  "fallbackUsed": false,
  "errorCode": null
}
```

## 8. 常见错误

- `404 No AI players found for game`
  - 说明该局还没有先 `generate` 或 `bootstrap`

- `404 No bound LLM config found for this AI player; generate or bootstrap players first`
  - 说明 `invoke` 没传 `llm`，但该 AI 又没有已绑定的服务端 LLM

- `404 No matching AI players found for role assignment`
  - 说明 `roles/assign` 传入的 `aiId` 没有匹配到当前局的 AI 玩家

- `404 No AI players found for this game`
  - 说明 `game/events/broadcast` 传了空的 `aiIds`、过滤后没有目标 AI，或者该局还没有先 `generate` / `bootstrap`

- `404 Memory state not found`
  - 说明查询 `GET /internal/ai/memory/{game_id}/{ai_id}` 时，该 AI 的 memory 尚未初始化或该 `aiId` 不存在

- `404 No persona assignment found for game`
  - 说明查询 `GET /internal/ai/persona/{game_id}` 时，该局还没有做过人格分配

- `422 Unprocessable Entity`
  - 说明请求体字段名、字段类型或枚举值不符合当前 schema

## 10. 狼人 privateVision 约定

当 `POST /internal/ai/agent/invoke` 的调用对象是狼人 AI 时，主游戏后端应当通过 `privateVision` 传入狼人专属的私有信息。

这条约定同时适用于：

- `stage = "vote"`
- `stage = "night_action"`

必填字段：

- `wolfTeammates`

推荐字段：

- `wolfTeammates`
- `consensusTarget`
- `wolfChat`
- `teammateMessages`
- `allowFriendlyFire`
- `forceConsensusTarget`
- `wolfDecisionMode`

字段含义：

- `wolfTeammates`：当前这只狼人已知的所有狼人队友，既包括 AI 狼，也包括真人狼
- `consensusTarget`：狼队协商后的优先击杀目标
- `wolfChat` / `teammateMessages`：来自狼人队友的讨论内容，其中也可以包含真人狼发送的消息
- `allowFriendlyFire`：这一回合是否允许投票或击杀狼人队友，默认应为 `false`
- `forceConsensusTarget`：当它为 `true` 时，只要 `consensusTarget` 合法，AI 就必须严格跟随该目标
- `wolfDecisionMode`：取值为 `auto_execute` 或 `advice_only`
- `auto_execute`（默认）：AI 狼人直接返回可执行的夜晚击杀动作
- `advice_only`：AI 狼人只返回建议目标和理由，不直接执行击杀

重要约束：

- `wolfTeammates` 中使用的玩家标识，必须与 `candidateTargets`、`alivePlayers` 中使用的标识完全一致
- 例如：如果真人狼在系统中的 id 是 `host`，那么 `wolfTeammates`、`candidateTargets`、`alivePlayers` 里都应该统一写成 `host`
- 如果省略 `wolfTeammates`，AI 服务会把真人狼队友当成普通候选目标处理
- 当前 AI 服务的默认行为是：只要传入了 `wolfTeammates`，且 `allowFriendlyFire` 不为 `true`，狼人投票和狼人夜晚击杀都会自动规避队友
- 如果 `forceConsensusTarget=true` 且 `consensusTarget` 合法，AI 服务会把狼人夜晚击杀目标强制对齐到这个目标
- 如果 `wolfDecisionMode=advice_only`，AI 服务会返回 `skillType=pass`，同时把建议目标保留在 `nightAction.killTarget` 中，并把 `nightAction.passReason` 设为 `advice_only_human_wolf_decides`

### 10.1 真人狼 + AI 狼：使用单 AI 接口

当场上至少还有一名存活狼人是真人玩家时，主游戏后端应继续使用：

- `POST /internal/ai/agent/invoke`

这条路径用于“真人狼 + AI 狼协同”的夜晚处理。每个 AI 狼人都会被独立调用一次。至于最终是不是由真人狼拍板，或者主后端是否已经提前形成了统一目标，由主游戏后端负责判断。

推荐调用方式：

- 如果是真人狼想先听 AI 狼建议：
- 调用 `POST /internal/ai/agent/invoke`
- `stage = "night_action"`
- 设置 `privateVision.wolfDecisionMode = "advice_only"`
- 这一条路径下不要再调用 `/internal/ai/werewolf/night-consensus`
- 如果真人狼或主后端已经决定了最终击杀目标：
- 调用 `POST /internal/ai/agent/invoke`
- `stage = "night_action"`
- 设置 `privateVision.consensusTarget`
- 设置 `privateVision.forceConsensusTarget = true`
- 需要的话可以继续保留 `privateVision.wolfDecisionMode = "auto_execute"`

简而言之：

- 真人狼与 AI 狼混合的夜晚处理，走 `POST /internal/ai/agent/invoke`
- 同一晚不要把这条路径和 `/internal/ai/werewolf/night-consensus` 混着用

### 10.2 全部存活狼人都是 AI：先走团队共识接口

当场上所有存活狼人都是 AI 时，主游戏后端应先调用一个单独的团队接口：

- `POST /internal/ai/werewolf/night-consensus`

这条路径用于“全 AI 狼团队协同”的夜晚处理。它本身不直接执行最终击杀，而是负责：

1. 先以 `advice_only` 模式调用每一只 AI 狼
2. 汇总所有 AI 狼给出的建议
3. 返回一个统一的 `consensusTarget`
4. 返回统一的 `privateVision`，用于回填给所有 AI 狼执行正式 `night_action`

请求示例：

```json
{
  "requestId": "req_wolf_team_1",
  "gameId": "game1",
  "werewolfAiIds": ["ai_2", "ai_6", "ai_8"],
  "visibleEvents": [],
  "alivePlayers": ["ai_2", "ai_6", "ai_8", "player_1", "player_3", "player_5"],
  "candidateTargets": ["player_1", "player_3", "player_5"],
  "privateVision": {
    "wolfTeammates": ["ai_2", "ai_6", "ai_8"],
    "allowFriendlyFire": false
  }
}
```

返回重点：

- `adviceResults`：每个 AI 狼给出的建议目标、confidence、理由和建议文本
- `aggregateScores`：系统侧对每个候选目标做出的聚合结果
- `consensusTarget`：聚合后选出的最终共识目标
- `finalKillTarget`：显式返回给主后端的最终击杀目标
- `executionDecision`：可直接执行的、夜晚行动风格的最终团队决策对象
- `sharedPrivateVision`：统一回填给所有 AI 狼的 `privateVision`
- `sharedPrivateVision` 中至少应包含 `wolfTeammates`、`consensusTarget`、`forceConsensusTarget = true`、`wolfDecisionMode = "auto_execute"`
- `privateVisionByAiId`：按 AI 狼 id 分组的同一份回填数据，可直接继续喂给 `POST /internal/ai/agent/invoke`
- `consensusRecordedAiIds`：已经写入本次共识结果记忆的 AI 狼列表

形成共识后的第二步推荐调用：

- 你可以只挑一名 AI 狼继续执行，也可以把所有 AI 狼都再调用一遍，取决于主后端是否希望保留一致的重放过程
- 调用 `POST /internal/ai/agent/invoke`
- `stage = "night_action"`
- 使用返回中的 `sharedPrivateVision`，或者使用 `privateVisionByAiId` 中对应 AI 的那一份
- 因为这里会带上 `forceConsensusTarget = true`，所以所有 AI 狼最终都会对齐到同一个合法目标
- 如果主后端只关心最后到底杀谁，可以直接读取 `finalKillTarget`
- 如果主后端更希望拿到一个即取即用的动作对象，可以直接读取 `executionDecision`

简而言之：

- 全 AI 狼夜晚处理分两步：
- 第一步：`POST /internal/ai/werewolf/night-consensus`
- 第二步：`POST /internal/ai/agent/invoke`
- 如果你希望 AI 狼先各自独立给建议，再由后端统一收敛成共识，就不要跳过第 1 步
- 同一晚不要把“真人狼 + AI 狼”的路径和“全 AI 狼”的路径混用

最小投票示例：

```json
{
  "requestId": "req_vote_wolf_1",
  "gameId": "game1",
  "aiId": "ai_1",
  "stage": "vote",
  "alivePlayers": ["host", "ai_1", "ai_3", "ai_4"],
  "candidateTargets": ["host", "ai_3", "ai_4"],
  "privateVision": {
    "wolfTeammates": ["host", "ai_1"],
    "allowFriendlyFire": false
  },
  "asyncMode": false
}
```

推荐的夜晚击杀示例：

```json
{
  "requestId": "req_night_wolf_1",
  "gameId": "game1",
  "aiId": "ai_1",
  "stage": "night_action",
  "alivePlayers": ["host", "ai_1", "ai_3", "ai_4"],
  "candidateTargets": ["host", "ai_3", "ai_4"],
  "privateVision": {
    "wolfTeammates": ["host", "ai_1"],
    "consensusTarget": "ai_3",
    "allowFriendlyFire": false,
    "wolfChat": [
      {
        "speaker": "host",
        "content": "Tonight eliminate ai_3 first."
      }
    ]
  },
  "asyncMode": false
}
```

全 AI 共识后的 `night_action` 跟进示例：

```json
{
  "requestId": "req_night_wolf_execute_1",
  "gameId": "game1",
  "aiId": "ai_2",
  "stage": "night_action",
  "alivePlayers": ["ai_2", "ai_6", "ai_8", "player_1", "player_3", "player_5"],
  "candidateTargets": ["player_1", "player_3", "player_5"],
  "privateVision": {
    "wolfTeammates": ["ai_2", "ai_6", "ai_8"],
    "consensusTarget": "player_5",
    "forceConsensusTarget": true,
    "wolfDecisionMode": "auto_execute",

}
```
## 11. 公共事件广播约定

对于所有玩家都能观察到的公共游戏事件，主游戏后端应优先使用：

- `POST /internal/ai/game/events/broadcast`

而不是循环调用：

- `POST /internal/ai/memory/event`

这个接口用于写入全体共享的游戏历史，尤其适合接收真人玩家语音转文字后的公共内容。

推荐使用场景：

- 真人玩家白天发言的文本转写
- AI 发言在主后端确认通过后的文本内容
- 公开投票动作和投票结果
- 放逐 / 死亡 / 公告等公共事件
- 任何应该被同局所有 AI 一起记住的公共信息

不要把下面这些角色私有信息通过这个接口广播：

- 狼人队友身份或狼队夜聊内容
- 预言家的查验结果
- 女巫当夜被刀目标，以及解药 / 毒药是否可用
- 猎人当前是否允许开枪

这些私有信息仍然应该通过下面的接口，以 `privateVision` 的形式传入：

- `POST /internal/ai/agent/invoke`

请求体示例：

```json
{
  "gameId": "game1",
  "event": {
    "day": 1,
    "stage": 1,
    "eventType": "speech",
    "speaker": "player_3",
    "content": "我怀疑 2 号玩家身份有问题",
    "weight": 1.0,
    "targets": ["player_2"]
  },
  "candidateTargets": ["player_1", "player_2", "ai_1", "ai_2"],
  "asyncMode": true
}
```

投票事件示例：

```json
{
  "gameId": "game1",
  "event": {
    "day": 1,
    "stage": 2,
    "eventType": "vote",
    "speaker": "player_5",
    "content": "vote -> player_2",
    "weight": 1.0,
    "targets": ["player_2"]
  },
  "candidateTargets": ["player_1", "player_2", "ai_1", "ai_2"],
  "asyncMode": true
}
```

返回重点：

- `appliedAiIds`：这次实际收到事件的 AI 玩家列表
- `states`：每个受影响 AI 的最新 memory 状态
- 如果请求里带了 `candidateTargets`，服务端还会为这些 AI 重新计算 `suspicionScores`

注意事项：

- 该局游戏必须已经先通过 `generate` 或 `bootstrap` 创建过 AI 玩家
- `event` 字段结构遵循 `AgentMemoryItem`
- 当前的 `event.stage` 是整数阶段编号
- 服务端会基于事件签名做简单去重，避免同一条公共事件被无限重复写入

## 12. 主后端接入更新

当前推荐的主游戏后端接入流程如下：

1. 开局时先确定 `aiCount`
2. 调用 `POST /internal/ai/bootstrap`
3. 调用 `POST /internal/ai/players/roles/assign` 分配具体角色
4. 每当出现新的公共事件时，调用 `POST /internal/ai/game/events/broadcast`
5. 只有在你明确想给某一个 AI 单独写 memory 时，才调用 `POST /internal/ai/memory/event`
6. 当轮到某个 AI 发言、投票或出技能时，调用 `POST /internal/ai/agent/invoke`
7. 处理狼人夜晚时，必须二选一：
   - 如果至少有一名存活狼人是真人玩家，就走 `POST /internal/ai/agent/invoke`
   - 如果所有存活狼人都是 AI，就先调用 `POST /internal/ai/werewolf/night-consensus`，再调用 `POST /internal/ai/agent/invoke` 执行正式夜晚动作
8. 所有角色专属的隐藏信息，都通过 `privateVision` 传递

如果是 STT / TTS 集成场景，推荐流程如下：

1. 主后端接收语音
2. 主后端调用 STT 得到文本
3. 主后端把转写结果通过 `POST /internal/ai/game/events/broadcast` 广播出去
4. 当下一个 AI 需要发言或投票时，主后端调用 `POST /internal/ai/agent/invoke`
5. 收到 `speechText` 后，主后端再调用 TTS
