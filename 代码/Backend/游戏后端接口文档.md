# 接口文档

## 1. 文档范围

本文档描述当前狼人杀主游戏后端对前端暴露的接口，来源以实际代码为准：

- 后端路由：`server/routes/index.js`
- 前端封装：`client/src/api/*.js`
- HTTP 服务默认端口：`6001`
- 前端开发服务默认端口：`6002`
- WebSocket 默认端口：`6003`

前端开发时通常通过 React dev server 代理访问，所以代码里使用 `/api/...` 即可。

## 2. 通用约定

### 2.1 鉴权

除以下接口外，路径中带 `/auth` 的接口都需要登录态：

- `POST /api/login`
- `POST /api/register`
- `GET /api/game/replay/file`

登录成功后后端返回 `accessToken`。前端需要把 token 放到请求头：

```http
authorization: <accessToken>
```

当前前端统一在 `client/src/common/fetch.js` 中自动注入该 header。

### 2.2 统一返回结构

成功：

```json
{
  "success": true,
  "data": {},
  "errorCode": null,
  "errorMessage": null
}
```

失败：

```json
{
  "success": false,
  "data": null,
  "errorCode": -1,
  "errorMessage": "错误原因"
}
```

前端 `fetch` 拦截器会把成功响应解包为 `data`，失败时弹出 `errorMessage` 并 reject。

### 2.3 常用枚举

游戏状态 `game.status`：

| 值 | 含义 |
| --- | --- |
| `1` | 游戏中 |
| `2` | 正常结束 |
| `3` | 房主手动结束 |

房间状态 `room.status`：

| 值 | 含义 |
| --- | --- |
| `0` | 准备中 |
| `1` | 游戏中 |

玩家状态 `player.status`：

| 值 | 含义 |
| --- | --- |
| `1` | 存活 |
| `0` | 出局 |

游戏阶段 `game.stage`：

| 值 | 阶段 | 前端含义 |
| --- | --- | --- |
| `0` | 夜晚开始 | 天黑请闭眼/进入夜晚 |
| `1` | 预言家阶段 | 预言家查验 |
| `2` | 狼人阶段 | 狼人袭击/狼人夜间交流 |
| `3` | 女巫阶段 | 女巫救人/毒人 |
| `4` | 天亮公布 | 公布夜晚死亡、猎人可开枪 |
| `5` | 发言阶段 | 存活玩家按顺序发言 |
| `6` | 投票阶段 | 普通公投 |
| `6.5` | PK 投票阶段 | 平票后的 PK 投票 |
| `7` | 遗言阶段 | 出局玩家遗言 |

角色 `role`：

| 值 | 含义 |
| --- | --- |
| `wolf` | 狼人 |
| `villager` | 村民 |
| `predictor` | 预言家 |
| `witch` | 女巫 |
| `hunter` | 猎人 |

阵营 `camp`：

| 值 | 含义 |
| --- | --- |
| `1` | 好人阵营 |
| `0` | 狼人阵营 |

## 3. 登录与用户

### 3.1 登录

`POST /api/login`

请求体：

```json
{
  "username": "host1",
  "password": "123456"
}
```

返回 `data`：

```json
{
  "accessToken": "jwt-token",
  "user": {
    "_id": 1,
    "username": "host1",
    "name": "host1",
    "roles": ["player"],
    "defaultRole": "player"
  }
}
```

### 3.2 注册

`POST /api/register`

请求体：

```json
{
  "username": "player001",
  "name": "玩家1",
  "password": "123456"
}
```

说明：注册接口默认创建普通玩家角色 `player`。

### 3.3 获取当前用户信息

`GET /api/user/getUserInfo/auth`

返回 `data`：当前登录用户信息。

### 3.4 创建用户

`POST /api/user/create/auth`

请求体：

```json
{
  "username": "player002",
  "name": "玩家2",
  "password": "123456",
  "role": "player"
}
```

## 5. 游戏主流程

### 5.1 开始游戏

`POST /api/game/start/auth`

请求体：

```json
{
  "id": 29,
  "setting": {
    "playerCount": 6,
    "p1": 30,
    "p2": 45,
    "p3": 30,
    "witchSaveSelf": 2,
    "winCondition": 1,
    "flatTicket": 1
  }
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 房间 ID |
| `setting.playerCount` | 本局玩家人数 |
| `setting.p1` | 预言家阶段倒计时 |
| `setting.p2` | 狼人阶段倒计时 |
| `setting.p3` | 女巫阶段倒计时 |
| `setting.witchSaveSelf` | 女巫自救规则 |
| `setting.winCondition` | 胜利条件 |
| `setting.flatTicket` | 平票规则 |

返回 `data`：

```json
{
  "message": "创建游戏成功！",
  "gameId": 230,
  "players": [
    { "number": 1, "role": "predictor" }
  ],
  "autoAiPlayers": []
}
```

说明：

- 只有房主可以开始游戏。
- 如果座位未坐满，后端当前会尝试自动补 AI 玩家。

## 7. 发言与遗言

### 7.1 发言/遗言是怎么实现的

发言和遗言是前后端共同完成的：

后端负责：

- 生成发言顺序或遗言顺序。
- 判断当前是否轮到该玩家。
- 保存最终文本到游戏记录。
- 发言/遗言结束后推进到下一个发言人。
- 所有人说完后自动推进阶段。

前端负责：

- 根据 `gameDetail.stage` 展示按钮。
- 根据 `gameDetail.speechTurn.currentSpeaker` 判断当前用户能不能发言。
- 使用浏览器麦克风和实时语音识别。
- 实时通过 WebSocket 广播字幕和音频。
- 结束后调用后端接口保存最终文本。

### 7.2 发言阶段提交文本

`POST /api/voice/speech/auth`

请求体：

```json
{
  "roomId": 29,
  "gameId": 230,
  "text": "我觉得 2 号发言不太好。"
}
```

返回 `data`：

```json
{
  "text": "我觉得 2 号发言不太好。",
  "recordId": 1001,
  "from": {
    "username": "player003",
    "name": "玩家3",
    "position": 4
  },
  "nextSpeaker": {
    "username": "player004",
    "name": "玩家4",
    "position": 5
  }
}
```

规则：

- 只能在 `stage = 5` 调用。
- 只有存活玩家可以发言。
- 必须轮到当前玩家。
- 保存成功后，后端会调用 `advanceSpeechTurn` 推进到下一个发言人。
- 如果所有人发言结束，后端会异步推进到下一阶段。

兼容说明：

- 该接口也兼容 `multipart/form-data` 上传 `audio`，后端会先转文字再保存。
- 当前推荐前端直接传 `text`，因为前端已经做了实时转文字。

### 7.3 保存遗言

`POST /api/game/saveLastWords/auth`

请求体：

```json
{
  "roomId": 29,
  "gameId": 230,
  "content": "我的遗言是，重点看 3 号。",
  "audioUrl": "",
  "userInfo": {
    "username": "player003",
    "name": "玩家3",
    "position": 4
  }
}
```

返回 `data`：

```json
{
  "message": "遗言保存成功",
  "data": {
    "_id": 1002
  },
  "nextSpeaker": null
}
```

当前规则：

- 只能在 `stage = 7` 调用。
- 当前玩家必须已经出局。
- 必须轮到当前玩家。
- 当前代码中仍有“第 2 天及以后死亡玩家没有遗言”的限制。

设计提醒：

- 如果后续按正式规则优化，需要把遗言来源拆成 `night` 和 `vote`。
- 首夜夜死遗言结束后应进入 `stage = 5` 发言。
- 白天票死遗言结束后应进入 `stage = 0` 下一晚。
- 第 2 天及以后夜死无遗言，但票死仍应有遗言。

### 7.4 获取发言/遗言记录

发言和遗言记录会随 `GET /api/game/info/auth` 返回：

```json
{
  "speechRecords": [
    {
      "_id": 1001,
      "day": 2,
      "stage": 5,
      "type": "speech",
      "text": "我觉得 2 号像狼",
      "source": "human",
      "from": {
        "username": "player003",
        "name": "玩家3",
        "position": 4
      }
    },
    {
      "_id": 1002,
      "day": 2,
      "stage": 7,
      "type": "lastWords",
      "text": "我的遗言是看 3 号",
      "source": "player",
      "from": {
        "username": "player004",
        "name": "玩家4",
        "position": 5
      }
    }
  ]
}
```

前端应把 `speechRecords` 渲染成屏幕上的发言记录，不要只依赖实时字幕浮窗。

## 8. 语音接口

### 8.1 语音转文字

`POST /api/voice/stt/auth`

Content-Type：`multipart/form-data`

表单字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `audio` | 是 | 音频文件 |

返回 `data`：

```json
{
  "text": "识别后的文字"
}
```

说明：

- 这是传统“录完一整段再上传识别”的接口。
- 当前发言阶段推荐用浏览器实时识别后，直接调用 `/api/voice/speech/auth` 提交 `text`。

### 8.2 文字转语音

`POST /api/voice/tts/auth`

请求体：

```json
{
  "text": "需要朗读的文字",
  "speaker": "可选",
  "sampleRate": 16000,
  "speechRate": 1
}
```

返回：`audio/mpeg` 二进制音频。

说明：

- 当前可用于 AI 发言朗读。
- 真人发言/遗言不建议再用 TTS 朗读一遍，应实时传音并保存文字。

### 8.3 提交发言

同 7.2：

`POST /api/voice/speech/auth`

支持两种方式：

方式一，推荐：

```json
{
  "roomId": 29,
  "gameId": 230,
  "text": "实时识别得到的最终文本"
}
```

方式二，兼容旧逻辑：

`multipart/form-data`：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `roomId` | 是 | 房间 ID |
| `gameId` | 是 | 游戏 ID |
| `audio` | 是 | 音频文件 |

## 9. WebSocket

### 9.1 连接地址

```text
ws://localhost:6003/lrs/{roomId}
```

前端当前使用 `react-websocket` 建立连接。

### 9.2 后端主动消息

后端可能向房间广播以下纯字符串：

| 消息 | 前端动作 |
| --- | --- |
| `refreshRoom` | 重新拉取房间信息 |
| `gameStart` | 游戏开始，重新进入游戏信息 |
| `stageChange` | 阶段变化，重新拉取游戏信息 |
| `refreshGame` | 重新拉取游戏信息 |

后端也会广播 JSON 字符串。前端应先尝试 `JSON.parse`，失败则按普通字符串处理。

### 9.3 实时发言字幕

前端发送：

```json
{
  "type": "realtimeSpeechText",
  "roomId": 29,
  "gameId": 230,
  "stage": 5,
  "speechType": "speech",
  "senderUsername": "player003",
  "senderName": "玩家3",
  "senderPosition": 4,
  "text": "我觉得二号",
  "isFinal": false,
  "timestamp": "2026-05-19T10:00:00.000Z"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `speechType` | `speech` 发言，`lastWords` 遗言 |
| `isFinal` | 是否最终文本 |
| `text` | 实时识别文本 |

后端会把该 JSON 转发给同房间所有连接。

### 9.4 实时发言音频

前端发送：

```json
{
  "type": "realtimeSpeechAudio",
  "roomId": 29,
  "gameId": 230,
  "stage": 5,
  "speechType": "speech",
  "senderUsername": "player003",
  "senderName": "玩家3",
  "senderPosition": 4,
  "mimeType": "audio/webm",
  "audioData": "data:audio/webm;base64,...",
  "timestamp": "2026-05-19T10:00:00.000Z"
}
```

说明：

- `audioData` 是 DataURL。
- 接收方应忽略自己发出的音频。

## 12. 前端调用建议

### 12.1 房间页初始化

推荐流程：

1. 登录后拿到 `accessToken`。
2. 创建或加入房间。
3. 调 `GET /api/room/info/auth` 获取房间详情。
4. 建立 WebSocket：`ws://localhost:6003/lrs/{roomId}`。
5. 如果 `room.status === 1`，调 `GET /api/game/info/auth` 获取游戏状态。

### 12.2 游戏中刷新策略

收到 WebSocket 消息时：

| 消息 | 建议处理 |
| --- | --- |
| `refreshRoom` | 调 `getRoomInfo` |
| `gameStart` | 调 `getRoomInfo` 后进入游戏 |
| `stageChange` | 调 `getGameInfo` |
| `refreshGame` | 调 `getGameInfo` |
| JSON `realtimeSpeechText` | 更新实时字幕 |
| JSON `realtimeSpeechAudio` | 播放对方音频 |

### 12.3 技能按钮展示

不要在前端硬编码太多规则。优先使用后端返回：

```json
{
  "skill": [
    { "key": "check", "name": "查验", "canUse": true, "show": true }
  ],
  "action": [
    { "key": "vote", "name": "投票", "canUse": true, "show": true }
  ]
}
```

前端建议：

- `show === true` 才显示按钮。
- `canUse === false` 时禁用按钮或提示已使用/未到阶段。

### 12.4 发言/遗言按钮展示

发言阶段：

```js
gameDetail.stage === 5 &&
gameDetail.speechTurn?.currentSpeaker?.username === currentRole.username &&
currentRole.status === 1
```

遗言阶段：

```js
gameDetail.stage === 7 &&
gameDetail.speechTurn?.currentSpeaker?.username === currentRole.username &&
currentRole.status === 0
```

结束录音后：

- 发言调用 `POST /api/voice/speech/auth`。
- 遗言调用 `POST /api/game/saveLastWords/auth`。
- 成功后重新调用 `GET /api/game/info/auth`，让 `speechRecords` 和 `speechTurn` 刷新。

## 13. 当前已知规则缺口

遗言规则当前还没有完全按正式狼人杀规则拆分：

- 当前 `stage = 7` 同时承担夜死遗言和票死遗言。
- 当前 `saveLastWords` 里有“第 2 天及以后死亡玩家没有遗言”的限制。
- 正式规则应该是：
  - 首夜夜死有遗言。
  - 第 2 天及以后夜死无遗言。
  - 每轮白天票死都有遗言机会。
  - 首夜夜死遗言结束后进入发言阶段。
  - 票死遗言结束后进入下一个夜晚。

建议后续后端增加遗言来源字段：

```json
{
  "lastWordsReason": "night",
  "nextStageAfterLastWords": 5
}
```

或：

```json
{
  "lastWordsReason": "vote",
  "nextStageAfterLastWords": 0
}
```

这样前端可以准确展示“首夜死亡遗言”或“投票出局遗言”，后端也能准确决定遗言结束后跳转到哪个阶段。
